핵심 결과후보 없던 15건바뀐 구조실험 비교실제 처리 과정방식 이름을 가린 평가연구 대시보드

전체 그림

17개를 모두 통과해야 했던 것이 아닙니다. 기존에는 그 17개 안에서만 수정 후보를 만들었습니다.

새 버전은 KG의 말단 지식을 간결한 문법 카드로 읽고, Qwen이 현재 문장에 맞는 수정 계획과 활용형을 만듭니다. 규칙마다 Python 변환 함수를 추가하지 않습니다.

문장이 바뀌었다는 것은 방언이 좋아졌다는 뜻이 아닙니다. 자연스러움과 의미 보존은 옆 평가 화면에서 사람이 확인해야 합니다.

1. 후보가 없었던 15건: 서로 다른 원인

기존 Single·Multi에서 모두 후보 0이었던 입력만 대조했습니다. ‘기존 코드가 처리하지 못함’, ‘표준어와 공유하는 형태’, ‘추가 활용 조건이 필요함’을 구별합니다. 아래의 설명은 원문과 기존 코드를 대조한 연구자의 해석입니다.

D02 = 경북방언 종결어미 연구 · D07 = 표준어 간섭 및 방언 의식으로 인한 경남 함양 방언 문법 형태의 변화 연구. 쪽수는 PDF 첫 페이지를 1로 센 위치입니다. 원본 PDF 해시를 기존 문헌 버전과 대조했습니다.

입력 / 현상기존 병목실제 KG 및 문헌이번 출력

2. 간결한 규칙이란 무엇인가

문법 카드: 재사용하는 지식

어떤 조건에서 어떤 형태를 쓸 수 있는지 저장합니다. ID·모듈·종류·제목·조건·형태·제약의 7개 항목입니다. 출처와 검토 이력은 같은 ID로 별도 연결합니다.

문장 수정 계획: 이번 입력에만 해당

‘W5 어절을, 이 카드들을 근거로, 이 기능을 유지하며 바꾼다’는 지시입니다. Single은 활용형까지 작성합니다. Multi는 다음 Worker에게 활용형 생성을 맡깁니다.

공통 Python 코드

실제 KG ID인지, 원문 어절인지, 수정이 겹치지 않는지 검사하고 완성 어절을 원문에 끼웁니다. 문법별 함수 721개를 작성하는 구조가 아닙니다.

줄인 정보와 남긴 정보

scope_profile 같은 운영 설명과 승인·활성화 상태는 생성용 카드에서 뺐습니다. 어휘, 받침, 시제, 문장 기능, 화계, 실제 금지 조건은 남겼습니다. 원본 KG와 출처는 삭제하지 않았습니다. 새 파일 카드는 실제 Neo4j ID·연결 경로와 결합하는 실행용 보기입니다. DB의 원본 노드를 덮어쓰지 않았습니다. DB에 남은 runtime_active=false는 과거 설계 기록이며, 새 실행기는 이 값이나 이전 17개 목록으로 적용 대상을 제한하지 않습니다.

721개를 모두 참이라고 재검증한 것은 아닙니다. 기존 해석·관찰·형태 목록도 종류를 구별해 검색합니다. 모델에 전달할 때 관련 모듈 안에서 기능별 다양성과 점수로 최대 48개를 선별합니다. 따라서 검색 순위에 따른 누락 가능성은 남습니다.

뒤쪽에서 비교한 두 방식

Single

Qwen 한 호출이 계획과 활용형을 함께 작성 → 공통 검사 → 원문에 조립

Multi

Qwen Planner가 계획 작성 → Qwen Worker가 활용형 작성 → 같은 공통 검사 → 원문에 조립

Single도 공통 분석 호출이 앞에 있습니다. 전체 파이프라인이 단 한 번의 LLM 호출이라는 뜻은 아닙니다. 무작위 분기, 화용 상황 추정, 상용 LLM 증류는 이번 범위에 넣지 않았습니다.

3. 실제 실험 결과와 비용

형식 통과는 실행 검사 결과입니다. 이전 버전과는 분석·후보 생성·조립 방식이 함께 바뀌었습니다. 이전 대비 차이를 17개 제한 해제 하나의 인과 효과로 해석할 수 없습니다. 새 Single/Multi끼리는 분석·조회·카드를 동일하게 공유했습니다.

다음 우선순위는 규칙 수 증가나 Agent 추가가 아니라, 분석 검증·공통 조건 판정·활용 조합의 분리입니다. 어간 종류·받침·원래 어미·시제·부정·높임을 공통 검사 항목으로 만들고, 각 카드에는 그 값만 넣는 방식이 가능합니다. 문법마다 Python 함수를 만드는 방식과 다릅니다.

추가 모델 호출 없는 소규모 조합 점검

이 세 예시는 다음 구현의 가능성을 점검한 것입니다. 이번 50건 출력을 사후 교정하지 않았으며, 모든 방언 활용에 대한 검증도 아닙니다.

별도로, 응답 끝에 공백이 반복되어 JSON이 완성되지 않는 현상도 발견했습니다. 이는 문법 지식의 부족과 구별해야 합니다. 다음 실험에서는 짧은 개발 예문으로 구조화 출력 방식·필드 구성·서버 설정을 따로 비교해야 합니다. 공백 반복의 내부 원인을 특정 서버 구현의 결함으로 확정한 것은 아닙니다.

또한 4건은 모델이 공백이 있는 구절을 제안했는데, 이번 구현의 ‘한 어절만 출력’ 제한이 거부했습니다. 예: 봐 가지고, 재밌어 가지고. 이것을 모두 언어적으로 틀렸다고 판정할 수는 없습니다. 다음 구현에서는 원문 위치는 유지하면서 한 구간을 여러 어절로 바꾸는 편집도 허용하고, 중복 내용은 별도로 검사해야 합니다.

후속 진행 순서

  1. 방식 이름을 가린 평가에서 자연스러움과 의미 보존을 확인합니다. 평가 전에는 개선을 확정하지 않습니다.
  2. 어색한 출력의 분석 → 선택 카드 → 지시 → 활용형을 역추적합니다. 분석 오류, 검색 누락, 잘못된 적용, 활용 오류를 구분합니다.
  3. 검색 누락이면 카드 선별을, 활용 오류이면 생성 지시나 공통 형태 조합을 수정합니다. 규칙 수 증가만 목표로 삼지 않습니다.
  4. 필요하면 동일 파이프라인에서 구 17개 카드만 허용한 조건을 별도로 비교해 제한의 영향을 분리합니다. 이 통제 조건은 이번에 실행하지 않았습니다.
  5. 개선 후에는 이번 50건과 구별한 새 입력·지역 화자 평가로 확인합니다.

어절 여러 개를 합치거나 나누는 변화, 조사 생략·어순 재배치 등은 현재 ‘어절 단위 치환’의 범위를 넘습니다. 이런 오류가 확인되면 구간 단위 계획으로 확장할 근거가 됩니다.
