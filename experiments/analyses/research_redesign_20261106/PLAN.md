# KG 검증과 Qwen 역할 분담 — 연구 재설계안

작성: 2026-11-06. 상태: 검토·논의용 계획. 이번 문서는 새 Qwen 실험 결과가 아니다. 기존 구현·원본 KG·실험 기록은 바꾸지 않는다.

## 1. 이번에 답해야 할 질문

우리의 목표는 ‘KG를 썼다’거나 ‘에이전트가 많다’를 보이는 것이 아니다. **같은 모델이 필요한 문법 정보를 더 정확하게 찾아, 뜻과 높임을 지키면서 자연스러운 방언을 만들 수 있는가**를 확인하는 것이다. 그래프가 조건표보다 낫지 않을 가능성도 결과로 받아들인다.

이번 제안에는 시험할 가치가 있는 아이디어와, 먼저 고쳐야 하는 전제가 함께 있다.

| 사용자 제안 | 판단 | 이유와 수정 방향 |
|---|---|---|
| 전체 노드·관계를 예문으로 한 번씩 통과 | 전체를 빠짐없이 검사하자는 목적에는 동의. 검사 방법은 분리 | 문헌·쪽·관리 노드는 번역 규칙이 아니다. 전체는 구조·출처 검사, 문법 용법은 적용/비적용/모호한 예문 검사 |
| 문장 분석은 큰 문제가 없었음 | 최근 기록과 맞지 않음 | 금지·청유·높임·관계 방향 오류가 있다. 9개 개발 확인이 좋아져도 다른 판단이 나빠졌다 |
| 전달 정보가 많아 생성 모델이 잊음 | 가능한 가설, 아직 원인 확정 아님 | 정보 위치·관련성·충돌·분석 오류·모델 능력·출력 제한도 후보. 짧은 요청에서도 과거 손실이 관찰된 기존 기록을 함께 고려 |
| 같은 Qwen을 여러 역할로 나누기 | 비교할 가치가 있음 | 역할 분담 효과와 단순히 더 많이 호출한 효과를 구분해야 함. 같은 모델끼리 같은 오류에 동의할 수 있음 |
| Kiwi 제거 | 비교 조건으로 포함, 바로 제거하지 않음 | 위치 고정에는 유용하나 계세요 분석 등 오류도 있음. LLM의 구간·형태 분석 역시 따로 검사해야 함 |
| 단어마다 워커 배치 | 첫 후보로 권하지 않음 | 시제·높임·부정·본동사와 보조동사의 관계가 단어 경계를 넘고, 짧은 조사마다 호출하면 비용이 급증 |
| BLEU·토큰·시간으로 비교 | 비용 지표와 보조 문자 지표는 채택 | 자연스러움·뜻 보존을 BLEU 하나로 판정하지 않음. 독립 지역 화자의 평가를 주 지표로 유지 |

## 2. 현재 KG에 대한 답

원본 파일을 다시 집계했다. **12개 모듈과 연결 자료는 있지만 사용자가 말한 모든 기준을 만족하는 ‘검증 완료 KG’는 아니다.** 저장된 자료가 있다는 것과 그 의미를 조건으로 정제했다는 것을 구별해야 한다.

| 실제 원본 내용 | 수 | 검사 방법 |
|---|---:|---|
| 문헌 쪽 발췌 SourceSpan | 655 | 문헌·쪽·발췌 일치와 인용의 적절성 |
| 문헌 지식 항목 SourceAtom | 721 | 문장의 뜻을 해석해 조건·표현·예외로 정제했는지 |
| 문헌 SourceDocument | 7 | 자료 식별·공유 계통·전문 접근 가능성 |
| 나머지 설계·문법·관리 노드 | 242 | 모듈 소속, 역할, 연결 적절성, 실행/비실행 구분 |
| 합계 | 1,625 | 모든 ID에 검사 상태를 붙임 |
| 원본 관계 | 6,167 | 모든 연결에 종류·검사 방식·결과를 붙임 |

원본 관계에는 상호참조 2,841개, 문헌 발췌 인용 1,418개, 모듈 소속 911개 등이 있다. **상호참조선을 타는 것 자체가 문법 조건을 판정한 것은 아니다.** 모든 관계에 참/거짓 조건을 붙일 필요도 없다. ‘이 쪽은 이 문헌에 속한다’는 연결은 출처 연결이며, ‘부탁일 때 주이소를 후보로 삼는다’는 연결에 조건이 필요하다.

최근 후보는 2,320노드·7,476관계다. 조건 조회 용법 56개, 조건 묶음 57개, 조건 노드 145개가 들어 있다. 이 숫자는 전체 한국어 문법의 완성도가 아니다. 26묶음은 전부 현황대장에 있지만 전부 정제 완료는 아니다.

‘불필요한 정보’도 두 곳을 나눠 판단한다. 문헌 위치·해석 상태·변경 이력은 연구 저장소에 필요하다. 매번 생성 모델에 보내는 관리 설명·중복 식별자·큰 원문은 불필요할 수 있다. **저장 정보와 모델 전달 정보를 분리하고, 전달에서 덜어도 원본 근거는 삭제하지 않는다.**

## 3. KG를 어떻게 빠짐없이 검사할까

### 전체 검사와 문장 검사를 나눈다

| 검사 | 실제 하는 일 | 종료 기준과 산출물 |
|---|---|---|
| 전체 구조 검사 | 원본 1,625/6,167과 후보 2,320/7,476을 따로 고정. 모든 ID의 종류·참조·모듈 연결·검사 적용 여부 확인 | 모든 ID가 통과/문제/미확인/문장검사 비대상 중 하나로 기록. 비대상 이유 필수. `coverage_ledger` |
| 문헌→지식 검사 | 7종의 절·표·예문 단위로 현재 항목과 대조. 조건·사용 범위·예외·대안 해석 추출 | 문헌의 각 검토 구간에 연결된 항목 또는 제외 이유. 출처 없는 누락도 찾는 역방향 검사. `source_coverage` |
| 용법·분기 검사 | 각 적용 조건 묶음에 긍정 예문, 필수 조건 하나를 바꾼 반례, 문맥이 부족한 예문 생성 | 대상 분기에 정당한 시험 또는 도달 불가/정보 부족 이유가 존재. `scenario_suite` |
| 전체 처리 검사 | 예문→분석값→조회된 조건→전달 내용→최종 출력의 차이를 기록 | 처음 확인된 불일치와 원인 가설·해결안 연결. `trace_and_issue_ledger` |

경로를 전부 조합하는 무한한 탐색 대신, **실제 허용값의 유한 조합과 중요한 조건 쌍**을 검사한다. 서로 불가능한 조건 조합은 정상 문장으로 억지 생성하지 않고 모순으로 남긴다. 순환하는 상호참조의 모든 경로를 열거하지 않는다. 예문 수는 노드 수와 같지 않다. 한 예문이 여러 검사를 충족하면 재사용하되 검사마다 분모를 따로 유지한다.

예문을 만든 모델이 자기 예문을 정답 인증하지 않는다. 개발용 예문에 한해 Claude가 후보를 만들면 GPT가 조건과 관계를 독립 확인하고, 화자 판단이나 문맥이 필요한 경우 사람에게 올린다. 최종 평가 문장·참고답은 이 검토 루프와 분리한다. 모델 간 합의만으로 현대 방언 사실을 확정하지 않는다. 통과를 기대하는 규칙 ID·조건값은 실행 전에 고정한다. 실제 조회 결과를 본 뒤 기대값을 맞추지 않는다.

문장을 만들기 전에 **문법 특징값을 직접 조회기에 넣는 검사**부터 한다. 예를 들어 ‘요청, 공손함, 보조 주다’라는 입력값과 조건 하나만 다른 값을 넣으면 분석 모델의 실수 없이 조회 코드 자체를 검사할 수 있다. 후보에는 조건 묶음에서 조건으로 향하는 ALL 연결 261개, 허용값 연결 ACCEPTS 214개가 있다. 공유 조건과 OR 대안 때문에 하나를 거짓으로 바꿔도 다른 분기가 참일 수 있으므로 분기별·전체 결과를 함께 검사한다. 57개 긍정 객체에 조건 연결별 거짓/모름을 더하면 단순 산식은 579개지만, 이는 예문 수나 확정 검사 수가 아니다. 입력 관계·기본값·구성 조건까지 확인한 뒤 실제 검사 목록을 정한다.

검사대장 작성이 끝났다는 것과 KG가 옳다고 검증됐다는 것은 다르다. 모든 항목에 ‘미확인’만 붙여 품질 검증 완료로 처리할 수 없다. 전체 대장과 병행해 원문 대조를 진행하고, **근거·조건·반례가 확인된 범위만** 후속 실험의 지원 범위로 고정한다. 묶음별 항목 수는 중복 소속 때문에 합계 993이며 고유 항목은 911이다.

예: ‘창문 좀 닫아 주세요.’는 본동사 닫다와 보조 주다의 연결 및 부탁 기능을 시험할 수 있다. ‘창문이 닫혔어요.’는 부탁이 아닌 반례다. 이 두 문장을 단순히 ‘주이소가 나왔는가’로 채점하지 않고, 부탁 관계가 분석됐는지→올바른 지식이 조회됐는지→실제 요청에 담겼는지→의미를 지킨 출력인지 따로 본다. 이 예시는 검사 설계 설명이며 새 정답 번역을 확정한 것이 아니다.

반례에는 반드시 **대상 용법·분기 ID, 바꾼 조건 하나, 나머지 조건, 기대 판정**을 붙인다. ‘-어서의 이유 용법은 반례’처럼 대상을 생략하면 안 된다. 실제 INT_CONN_SEQ_AGA는 reason과 sequence를 모두 허용하므로 이유라는 것만으로 이 용법의 반례가 되지 않는다. 그래프 명세와 맞는가를 확인하는 검사와, 그 명세가 문헌 해석에 맞는가를 확인하는 검사는 따로 기록한다.

### 부족하거나 충돌할 때

원인은 ‘문헌 부족’과 ‘문헌 충돌’ 둘뿐이 아니다. 원문 추출 누락, 표 해석 오류, 정제 실수, 조건 연결 누락, 모델 분석 오류, 조회·선별 버그, 전달 내용 충돌, 생성 실패도 구분한다.

사람에게 올리는 항목은 **원문 위치와 해석 → 실제 충돌 → 선택 가능한 수정안 → 영향받는 용법·예문**을 한 화면에 제시한다. 사람이 문헌과 다른 현대 표현을 채택하면 실행 정책에서는 이를 우선할 수 있다. 단, 원문을 고쳐 쓰지 않고 별도의 ‘사용자 승인 지식’으로 승인자·날짜·범위·대체하는 규칙을 기록한다. 논문에서는 문헌 기반 지식과 사람 보완 지식의 효과를 구별한다.

## 4. 두 종류의 에이전트를 구분한다

### 연구를 진행하는 팀: GPT 리드 + Claude + GPT 검토자

| 담당 | 맡는 일 | 내야 할 결과 | 하지 않는 일 |
|---|---|---|---|
| GPT 리드 | 범위·실험 설계, 코드·버전 관리, 의견 대조, 집계 | 결정 기록, 실제 코드와 실행 증거, 다음 행동 | 모델 합의를 정답으로 선언 |
| Claude 검토자 | 원문 의미·현대 표현·조건·예외, 입력부터 출력까지 필요한 정보가 끊긴 위치, 불필요 전달 내용 | 문제 위치→짧은 근거→대안과 반례 | 최종 평가 정답을 생성 프롬프트에 투입 |
| GPT 검토자 | 그래프 분모·조회 경로, 코드·실험 조건·비용, 데이터 누출과 유리한 결과만 고르는 위험 | 재현 가능한 반례·고정조건 검사·수정안 | 코드 검사 통과를 자연스러움 인증으로 사용 |
| 사용자·지역 화자 | 현대 표현 허용 범위, 근거 충돌, 목표와 평가의 큰 결정 | 승인/수정 요청 및 적용 범위 | 모든 로그를 수작업으로 읽도록 강요받음 |

운영은 **독립 의견 → 서로의 반례 검토 → 리드의 채택·미채택 기록 → 필요한 항목만 사람 판단** 순서다. 초기 운영안은 독립 1회와 상호 검토 1회이며, 횟수가 연구 법칙이라는 뜻은 아니다. 해결되지 않은 사실 충돌은 토론 반복으로 없애지 않는다. 일반 코드 수정은 위임 범위에서 진행하되 목표·평가·생성 주체 변경은 사용자 결정이다. 다른 검토자에게 원본을 직접 덮어쓰게 하지 않는다.

외부 자료는 Claude가 공개 문헌·사전·용례를 찾아 출처와 사용 범위를 기록하고, GPT가 과도한 일반화·재인용 계통을 확인한다. 인터넷 예문 하나를 모든 경상도 문장에 적용하는 규칙으로 올리지 않는다. 최종 평가 문장·참고답은 지식 보완 단계에서 분리한다.

### 번역 실험 안의 팀: 동일한 Qwen을 역할별로 호출

서로 다른 역할·입출력·인계 기록을 가진 호출 묶음을 여기서는 ‘에이전트’라고 부른다. 이름만 바꾼 여러 호출이 자동으로 더 똑똑해지는 것은 아니다.

첫 후보는 **단어마다 워커를 만드는 방식 대신, 문장 전체를 보면서 서로 다른 책임을 맡기는 방식**이다.

| 역할 | 받는 정보 | 판단·출력 | 핵심 제한 |
|---|---|---|---|
| 분석 1: 구조 담당 | 원문 전체, 선택 조건에서 Kiwi 관찰값 | 절·서술어·명사구 구간, 본동사–보조동사·명사–조사 연결 | 방언을 생성하지 않음 |
| 분석 2: 의미 담당 | 같은 원문 전체와 구조 담당이 제안한 구간·관계 | 질문/부탁/금지, 시제·부정 범위, 주어/듣는 사람 높임 | 구조 제안이 틀려 보이면 충돌 표시. 없는 문맥은 미확정 |
| 연결 코드 | 두 분석과 원문 구간 | 정확한 위치·ID를 맞추고 충돌을 표시, KG 조건 조회 | 의미가 충돌하면 다수결로 사실 확정하지 않음 |
| 생성 담당 | 원문 전체, 조회한 관련 지식, 변경 후보와 보존할 뜻 | 문장 전체의 방언 초안 | 단어 결과를 기계적으로 이어붙이지 않음 |
| 점검 담당(비교 후보) | 원문·같은 지식·초안 | 잘못된 위치, 손실된 뜻·시제·높임, 근거가 없는 변경 | Claude 정답 없이 근거를 특정. 새 KG 사실 추가 금지 |
| 최종 작성 담당(비교 후보) | 원문·같은 지식·초안·점검 | 수정하거나 초안을 유지한 최종 문장 | 최종 작성도 Qwen. 코드가 대신 교정하지 않음 |

첫 비교는 **구조 담당 → 의미 담당의 순차 분업**으로 한다. 의미는 절·본용언/보조용언의 범위에 의존하므로, 병렬로 서로 다른 구간을 만드는 위험을 먼저 줄인다. 두 검토자의 반례를 받아 초기 병렬 제안을 수정했다. 구조 오류가 다음 단계에 전파될 위험은 남으므로 의미 담당도 이의를 표시할 수 있게 한다. 원문 문자 위치와 짧은 인용으로 결과를 연결하고, 특징별 작성자와 변경 이유를 남긴다. 충돌을 다수결이나 마지막 응답으로 덮지 않는다. 미확정 특징이 있다는 이유만으로 문장 전체를 무조건 원문 유지로 강제하지 않는다. 첫 비교에서는 무제한 중재 호출을 넣지 않는다. 병렬화는 품질 효과가 확인된 뒤의 별도 최적화이며, 같은 vLLM 서버에서는 병렬 호출이 곧 지연시간 절반을 뜻하지 않는다.

Kiwi 유무 비교에서는 원시 Kiwi 관찰을 보존하면서 **선택한 해석·작성 주체·근거 구간·후보 밖/모름**을 별도 저장한다. LLM이 고른 대안을 기록만 하고 조회에는 쓰지 않으면 대체 효과를 시험한 것이 아니다. 반대로 원시 관찰을 조용히 덮어쓰면 추적이 안 된다. LLM-only에는 Kiwi 값을 다른 필드로 몰래 제공하지 않고, 원문 위치를 검사하는 일반 코드는 양쪽에 똑같이 둔다. ‘안/못이 부사로 분석됨’ 자체를 오류라고 하지 않는다. 부정 정보를 모델과 KG에 연결하는 코드 문제인지 별도로 본다.

생성은 우선 **한 번 작성**과 **작성→점검→최종 작성(3호출)**을 비교한다. 3호출 조건은 오류가 없다고 판단해도 마지막 작성 단계에서 초안을 그대로 반환할 수 있으며 비용을 모두 센다. 이후 효과가 확인될 때만 필요한 경우에 점검·재작성을 호출하는 조건을 별도 시험한다. 현재 구현된 구조로 오해하지 말 것: 이 역할 분담은 제안이며 새 실행 전이다.

단어·형태소별 워커를 당장 만들지 않는다. 후속으로 필요하면 ‘본용언+보조용언’ 또는 ‘절’처럼 같이 해석해야 하는 묶음 단위로 나누고, 각 워커도 원문 전체와 공통 보존 정보를 받는다. 최대 동시 워커 수와 재결합 비용을 정한다. 12개 문법 모듈은 지식 분류이지 12개 에이전트를 반드시 만들라는 뜻이 아니다.

## 5. 한 번에 한 원인을 비교하는 실험

모델·KG·분석·전달·생성 구조를 한꺼번에 바꾸면 무엇이 좋아졌는지 알 수 없다. 아래 비교는 순서대로 시행하고, 효과가 없는 후보는 다음 단계의 기본으로 채택하지 않는다.

| 순서·질문 | 비교 조건 | 고정하는 것 | 결과와 종료 기준 |
|---|---|---|---|
| 1. 전체 현황과 조회 동작 | 전체 검사대장 + 특징값 직접 검사 + 조건표/그래프 반환 대조 | 원본/후보 버전 | 구조·조회 문제를 먼저 찾고 지원 범위 고정. 7종 의미 정제는 병행하되 미확인 범위는 품질 검증으로 세지 않음 |
| 2. 분석 오류인가, 전달 부담인가 | 저장 분석/검토자 수정 분석 × 기존 전달/관리 정보만 줄인 전달 | 생성 모델·지식 버전·디코딩·출력 지시 | 네 조건의 위치별 의미·시제·높임 오류와 반복 편차 비교. 수정 분석은 진단용 개입이며 사람 정답으로 부르지 않음 |
| 3. Kiwi와 분석 분업의 효과 | Kiwi+Qwen1, Kiwi+Qwen2역할, LLM단독1, LLM단독2역할 | KG·출력 분석 형식·진단 입력 | 위치/관계/기능 오류와 downstream 조회 적절성. 기존 검사기가 Kiwi를 정답으로 삼지 않게 독립 구간 주석 준비 |
| 4. 생성 분업의 효과 | 1회 생성 / 일반 재검토3회 / 역할분담3회 | 같은 분석·조회 지식·모델 | 역할이 다른 효과와 더 많이 호출한 효과 구분. 뜻·시제·높임 오류/자연스러움/비용 비교 |
| 5. 모델이 달라지면 | 개발에서 정한 기본 구조에 모델을 하나씩 교체 | KG·데이터·평가 규칙 | API 호환→소규모 개발→전체 비교. 모델별 템플릿과 토큰 한도·추론 모드 기록 |
| 6. 그래프의 효과 | 지식 없음 / 예문 / 문서 검색 / 조건표 / 그래프 | 같은 모델·입력·근거 원천·생성 구조 | 질과 비용의 이익·차이 없음·악화 모두 보고. 최종 평가 이전 설계 고정 |

분석2역할의 비용 차이를 해석할 때에는 같은 두 호출의 ‘분석 전체→일반 자기검토’ 대조를 둔다. 단일 분석+생성은2호출, 일반 자기검토+생성 및 역할 분업+생성은각3호출이다. 처음에는 역할을 나눈 효과와 한 번 더 생각한 효과를 구분한다. 단순 다수결은 2명에서는 성립하지 않는다. 전체 토큰 상한을 맞춘 비교와 실제 비용-품질 비교를 함께 보여 준다. 동일 호출 수만으로 동일 계산 비용이라고 하지 않는다.

**첫 유료/서버 호출 진단의 구체안:** 기존 노출 개발·회귀 입력에서 문법 현상·성공/실패 유형을 사전에 정해 16문장을 선정하고, 네 조건을 각3회 반복해 최대192생성호출로 비교한다. 새로 만든 ‘16문장 데이터셋’이 이미 있다는 뜻이 아니다. 선정 ID와 이유를 실행 전에 고정한다. 새로운 분석 호출은 하지 않으며 사용자 승인 번역문도 생성에 넣지 않는다. 이전199호출 예산과 별도인 새 실험안으로, 아직 실행하지 않았다. 동일 요청 반복의 변동을 이 진단에서 측정하며 3회만으로 미세한 차이가 확정된다고 주장하지 않는다. 조건 순서를 사전에 섞고 같은 동시성으로 실행한다.

네 조건은 ①저장 분석+기존 전달 ②저장 분석+관리 정보 축소 ③검토자 수정 분석+기존 전달 ④검토자 수정 분석+관리 정보 축소다. 분석 수정으로 조회 결과가 달라지는 것은 의도한 개입이다. 그러나 같은 분석 안에서는 선택된 지식·표현·조건·근거·보존 정보가 같아야 한다. 두 검토자는 수정한 필드·근거·미확정 값을 남기며, 언어학적으로 불확실한 결정만 사용자에게 요청한다. 이것을 모델의 실제 분석 성능 또는 완벽한 정답 분석으로 보고하지 않는다.

기존 오프라인 축소 대안은 **자료 선별과 관리 정보 축소가 함께** 들어 있으므로 이 네 조건에 그대로 재사용하지 않는다. 관리 정보만 줄이는 별도 투영을 만들고 실제 요청을 대조한다. 필요한 지식을 덜어낸다면 순수한 전달 부담 비교가 아니므로 실행 전에 수정한다. 이후 근거가 있을 때만 무관 참고 제외, 정보 위치(앞·중간·뒤), 짧은 결합형 설명 추가를 각각 별도 비교한다. 줄인 전달로 차이가 없다고 곧바로 ‘망각 가설이 거짓’이라 확정하지 않고 효과 크기·반복 편차·다른 설명을 확인한다.

실행 전 호출·토큰·마감 상한을 기록하고, 예를 들어 3회 연속 기술 실패 또는 최소10입력 이후20% 기술 실패 시 모든 조건을 함께 멈추는 정책을 고정한다. 숫자는 예산 명세에서 확정할 제안이며 성공할 때까지 자동 재시도하지 않는다. 실패·미시도도 분모에 남긴다. 분석 공유 실행의 물리 총비용과 각 방법을 독립 운영할 때의 비용은 별도로 계산한다.

운영 중단 기준과 효과 판정 기준은 다르다. 효과 판정에는 사전에 ‘실용적으로 의미 있는 차이 폭’과 사람 평가 지침을 정하고 짝 비교의 불확실성 구간을 본다. 지금 임의로 80% 같은 합격선을 넣지 않는다. 실제 요청 예시, 입력 ID, 반복·역할별 호출표, 비용 상한과 판정 기준이 갖춰지기 전에는 모델 실험 준비 완료로 표시하지 않는다.

후속 분석·생성 분업은 지원 문법을 고르게 포함한 개발24~36문장부터 규모를 정하는 안이다. 이는 이미 만들어진 데이터나 최종 평가 표본 수가 아니다. 문법 분모와 첫 진단의 변동을 확인한 뒤 수·예산을 정한다. 개선이 없거나 다른 오류가 늘면 같은 프롬프트를 계속 길게 쓰지 않는다. 한 차례 원인에 맞춘 수정 후 같은 실패가 반복되면 해당 설계의 한계로 정리하고 다음 대조로 넘어간다. 이전에 효과가 없었던 보존 경고→재작성 방식은 새로운 차이가 정의되지 않는 한 재실험하지 않는다.

### 그래프에 유리하게 비교하지 않는 방법

두 질문을 분리한다.

1. **제품 전체 비교:** 원문을 잘 나눠 검색·요약하는 문서 RAG와 우리 시스템을 비교한다. 일반 RAG를 일부러 긴 원문 전체 전달로 만들지 않는다. 그래프용 지식 정제 비용도 별도로 보고한다.
2. **그래프 구조만의 비교:** 동일하게 정제한 조건·표현·근거를 평문, 조건표, 그래프로 각각 표현한다. 조건표도 관계 정보를 손실 없이 표현할 수 있게 한다. 결과가 같으면 그래프의 품질 우월성을 주장하지 않는다. 이때 확장/추적/조회 비용이 다를 수 있으나 실제 측정해야 한다.

단계 분리 진단에서는 같은 사람이 확인한 분석값으로 검색만 비교하고, 최종 실험에서는 실제 모델 분석부터 모두 실행한다. 정답 분석을 사용한 진단을 실제 시스템 성능으로 보고하지 않는다. 생성 입력의 형식을 같게 하는 검색 비교와, 같은 선택 지식을 서로 다르게 표현하는 전달 비교도 나눈다.

조건표와 그래프의 선택 결과와 실제 요청이 완전히 같다면 생성 호출을 두 번 실행해 별개 방법의 독립 표본으로 세지 않는다. 조회 동등성·조회 시간은 따로 측정하고 같은 생성 요청은 재사용했다는 사실을 표시한다. ‘지식 없음’도 원문만 받는 zero-shot과 공통 분석은 받되 외부 지식만 없는 조건을 구분한다.

지금 남은 중요한 가설에는 **과거·높임과 실현형을 어떻게 결합하는지 설명이 부족한가**도 있다. 단순 ‘-어예’ 후보가 있다는 것과 과거형을 보존해 결합할 충분한 설명이 있다는 것은 다르다. 우선 호출 없이 오류 위치별 전달 내용을 읽고, 결합 설명의 유무와 적절성을 기록한다. 결합형이 문자로 쓰이지 않았다고 곧 지식이 틀렸다고 확정하지는 않는다. 정제 지식이 전달된 위치와 전달되지 않은 자유 생성 위치도 따로 집계한다.

| 개발·원인 진단 | 기존50, 이번30, 재사용18, 새 조건검사 예문 | 노출된 개발 자료로 표시. 오류를 보며 고칠 수 있음 |
| KG 조건 검사 | 지식에서 만든 긍정·반례·모호한 예문 | 경로 검사이지 독립 번역 품질 증명 아님 |
| 최종 평가 | 범위·방법을 고정한 뒤 준비하는 새 대화 문장 | 정답·검토 결과를 구현에 사용하지 않음. 같은 어휘 템플릿 변형도 분리해 누출 방지 |

최종 쉬운 데이터도 KG가 잘하는 문장만 보고 골라서는 안 된다. 사전에 정한 문법군·짧은/조금 긴 문장·변환이 필요 없는 대조·지원 밖의 작은 진단군을 구분한다. 미지원군은 지원군 점수에 섞어 덮지도 않고 조용히 빼지도 않는다. 최종 문장 수는 화자 평가 가능량과 개발 변동으로 정하며, 30~100개만으로 작은 차이를 확정할 수 있다고 보장하지 않는다.

주 지표는 방식 이름을 가린 경상도 화자의 **자연스러움**이다. 뜻이 바뀐 유창한 문장을 좋은 번역으로 세지 않도록 의미·시제·부정·높임 오류도 별도로 표시한다. 가능하면 둘 이상이 독립 평가하고 의견 차이도 남긴다. 지역/세대와 평가 지침을 기록하며 단일 화자 결과면 그 범위의 한계를 명시한다.

기존에 합의한 넓은 현대 경상도 표현 범위를 기본으로 유지한다. 새 지역·연령 필수 입력을 임의로 추가하지 않는다. 화계 대응이나 지역 표현이 실제로 충돌할 때 해당 항목만 사용자에게 제시한다. 평가자를 확보하지 못하면 개발 오류 분석까지 진행하되 독립 자연스러움 평가를 완료했다고 발표하지 않는다. 가능하면 참고 번역 작성자와 평가자를 분리한다. 방언 출력의 Kiwi 분석은 경고 수단이며, 형태소 수 감소만으로 과거 의미 소실을 확정하지 않는다. 공통형 유지·보존·차단 용법에서 원문 유지가 정당한 경우도 인정한다.

BLEU는 단어열, chrF는 글자열이 참고 번역과 얼마나 겹치는지 보는 보조 수치다. 표준어를 유지해도 높은 값이 나올 수 있고 자연스러운 다른 방언형이 낮은 값을 받을 수 있다. 정규화·토큰화·참고 개수·구현 버전을 고정한다. COMET 같은 평가 모델도 이 방언 과제에서 검증 없이 정답 판정기로 쓰지 않는다. Claude/GPT의 평가는 오류 진단에 쓰되, 자신이 만든 지식의 효과를 최종 인증하는 유일한 판정자로 쓰지 않는다.

전체 입력·출력 토큰, 모든 역할·재시도 호출 수, 실제 시작~종료 시간, 단계별 대기/생성 시간, 실패율을 기록한다. 모델이 다른 경우 토큰 한 개의 크기도 다르므로 실제 지연·처리문장 수·하드웨어도 함께 보고한다. 문장별 짝 비교와 불확실성 구간을 제시하고, 반복 호출을 서로 독립인 새 문장 수로 늘려 세지 않는다.

## 7. 검토·보고 및 다음 착수점

이번 산출물은 이 계획, 실제 KG 규모 재집계, 두 검토자의 독립/상호검토, 채택·보류 결정 기록이다. 새 Qwen 호출은 0회다. 사용자에게 키워드 대신 원문→관찰→문제→해결 후보를 보여 주고, 세부 JSON은 확인용 부록으로만 둔다.

**다음 착수점은 전체 KG의 역할별 검사대장과 실제 조건검사 목록을 만드는 것**이다. 그 결과로 어느 문법을 실행 비교에 쓸지 정하고, 단계2의 정보량 진단과 단계3·4의 역할분담 대조를 진행한다. KG 전체의 문장 생성 성공을 기다려야만 어떤 실험도 시작할 수 있는 구조는 아니다. 문제가 없는 범위는 고정해 비교하고, 나머지는 근거 있는 미완료 항목으로 계속 정제한다.

현재 사용자에게 수백 개 노드를 승인해 달라고 요청할 필요는 없다. 추후 필요한 결정은 문헌과 다른 현대 표현을 채택할 구체적 충돌, 최종 평가를 맡을 사람·지역 범위, 비교할 다음 모델의 제공 가능 환경이다. 일상적인 코드·검사 수정은 기존 위임을 따른다.

## 8. 확인한 선행 연구와 이번 연구에 가져올 점

아래는 이번에 추가 확인한 1차 자료다. 사용자가 다른 세션에서 작성 중인 논문의 전체 인용 목록과 동일하다고 주장하지 않는다.

- [TransAgents — Wu et al., TACL 2025](https://aclanthology.org/2025.tacl-1.42/): 번역·현지화·교정 역할을 나누는 사례. 초장문 문학 번역의 결과를 짧은 한국어 방언 변환에 그대로 적용할 수는 없다. 역할 분담 대조를 설계하는 근거로 사용한다.
- [Why Do Multi-Agent LLM Systems Fail? — Cemri et al., 2025](https://arxiv.org/abs/2503.13657): 설계·에이전트 간 불일치·검증 실패를 구분한다. 인계·종료·충돌 처리도 실험 변수로 기록할 이유다. 본 과제의 성능 효과를 증명하는 논문은 아니다.
- [Lost in the Middle — Liu et al., TACL 2024](https://aclanthology.org/2024.tacl-1.9/): 긴 문맥에서 관련 정보의 위치에 따라 성능이 달라지는 사례. 이번 Qwen의 방언 오류를 같은 원인으로 단정하지 않고 위치/길이 대조로 확인한다.
- [Experts, Errors, and Context — Freitag et al., TACL 2021](https://aclanthology.org/2021.tacl-1.87/): 명시적 오류 분류와 문맥을 제공한 사람 평가를 참고한다. 방언 사용자 평가에 맞춰 항목을 단순화하되 변경점을 기록한다.
- [BLEU — Papineni et al., ACL 2002](https://aclanthology.org/P02-1040/), [chrF — Popović, WMT 2015](https://aclanthology.org/W15-3049/): 참고 번역과의 겹침을 재현 가능한 보조 지표로 기록한다. 현대 방언 자연스러움 자체를 입증하는 지표로 취급하지 않는다.
- [COMET — Rei et al., EMNLP 2020](https://aclanthology.org/2020.emnlp-main.213/): 학습 기반 번역 평가의 비교 후보. 한국어 방언에서의 적합성은 별도 확인이 필요하다.
